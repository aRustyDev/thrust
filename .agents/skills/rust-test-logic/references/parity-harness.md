# Parity harness: the Rust side of a legacy-TypeScript comparison

Tags: `[re-run]` reproduced on this machine; `[zip]` recorded by the source's author, not re-run; `[derived]` read
from crate docs or source, not run.

**Scope.** The `ts-to-rust` skill owns the port: scoping, freezing the TypeScript's behaviour (corpus, lossless
encoder and controls, including the mutated fixture, pinned size and stale exceptions, in
`references/freeze-and-oracle.md`), types, the recorded-response oracle for HTTP surfaces, the exception register and
the JS-vs-Rust trap tables (`references/json-fidelity.md`, `references/type-map.md`). This page covers only what
that skill does not carry: how a Rust test crate discovers and replays fixtures, the live Node bridge, the
`parity_`/`oracle_` split, and a few traps.

## Whose format wins

When the unit is a port driven by `ts-to-rust` (structured values, errors, `undefined`/`NaN`/`-0`), its freeze wins:
its lossless encoder, message-text comparison, exception register, and "fixtures are never hand-edited". This page
then supplies only the Rust replay mechanics (datatest-stable discovery, the persistent bridge, prefix routing). The
templates `examples/gen-fixtures.mjs` and `examples/parity.rs` (`{ input, expected | error }`, integers as strings)
are for **scalar units** (strings and integers). Their error-kind-only policy applies only where error messages are
not observable. Intended differences from the TypeScript go in `ts-to-rust`'s exception register, never into a
fixture.

## Two layers

| Layer | Prefix | Runs | Needs |
|---|---|---|---|
| Golden fixtures recorded from TypeScript and committed | `parity_` | every `cargo nextest run` | nothing |
| Live comparison on generated inputs | `oracle_` | `--profile oracle` and `deep` only | Node.js and the built legacy package |

## `parity_`: datatest-stable, one test per fixture file

Use datatest-stable, not rstest's `#[files]`: rstest resolves its glob at compile time, so a new fixture file is
missed until the test target rebuilds (its docs suggest a `build.rs` with `rerun-if-changed`) `[derived]`.
datatest-stable lists files at run time, one nextest test per file (`parity_isqrt::isqrt-001-boundaries.json`
`[zip]`), so new fixtures run without recompiling. Template: `examples/parity.rs`.

```toml
# crates/<crate>/Cargo.toml
[dev-dependencies]
datatest-stable = "0.3"
serde = { version = "1", features = ["derive"] }
serde_json = "1"

[[test]]
name = "parity"
harness = false
```

Facts from datatest-stable 0.3.3 `[derived]`: `root` is relative to the crate root and `pattern` is a regex tested
against the path relative to `root`; a test `fn(&Path, String)` receives the file contents; a pattern that matches no
file panics (so an empty corpus fails). With `harness = false`, ordinary `#[test]` functions in the same target do not
run: put libtest guards in another test target.

- The template reports every divergence in a file, not just the first: a fixture mutated in two places produced one
  failure listing `2 divergence(s)` `[re-run]`. For structured outputs deserialize `expected` into
  `serde_json::Value` and compare values.
- **Recording (scalar units).** `TZ=UTC node legacy-oracle/gen-fixtures.mjs` regenerated byte-identical fixtures
  (equal sha1) `[re-run]`: the generator is deterministic (seeded PRNG) and writes the legacy commit into each file.
  Run it only when the legacy behaviour is the agreed reference, commit the output, never hand-edit it.
- An `oracle_` counterexample is a divergence too: triage it, then add the input to the frozen corpus (the generator
  for scalar units, `ts-to-rust`'s freeze otherwise) so the hermetic `parity_` layer covers it permanently.

## `oracle_`: a persistent Node bridge driven by proptest

Templates: `examples/ts-oracle.mjs` (Node side), `examples/oracle.rs` (Rust side), and `tests/common/mod.rs` for the
proptest config (`property.md`).

- `ts-oracle.mjs` reads one JSON request per line on stdin (`{"fn": "isqrt", "args": ["16"]}`) and writes one
  response per line (`{"ok": "4"}` or `{"error": "..."}`), in order, exiting when stdin closes. Add one adapter per
  ported function; **adapters wrap pure functions only, or stub their I/O**, so the oracle stays hermetic.
- The Rust side keeps one Node process per test process in a `static` (`OnceLock<Mutex<_>>`). Never spawn Node per
  case: 256 proptest cases went through one process in about 0.1 s `[re-run]`. nextest runs each test in its own
  process, so each `oracle_` test starts its own Node; the `ts-oracle` test group caps how many run at once
  (`nextest-profiles.md`).
- Integers travel as strings both ways and use `BigInt` on the JS side: a JS `number` is exact only to 2^53.
- `oracle_` tests are excluded from the default profile. Run them with `cargo nextest run --profile oracle` after the
  legacy package is built (`npm ci` and the build are the user's decision), or inside the `deep` profile with
  `PROPTEST_CASES=4096`.
- The proptest body compares Rust to the bridge's answer: `prop_assert_eq!(rust(n), legacy, "input {}", n)`.

Two limits of the template, both `[derived]` from reading it:

- The Rust side panics on **any** `{"error": ...}`, and the Node side turns every thrown exception into one. A unit
  that legitimately throws on some inputs needs an adapter that returns the failure as data (for example
  `{"ok": {"err": "<kind>"}}`) so the test can compare Err kinds; keep the panic for a broken bridge.
- `Command::new("node")` inherits the host's `TZ` and locale. A date- or `localeCompare`-sensitive unit needs
  `.env("TZ", "UTC")` (and a fixed locale) on the spawn, or the oracle differs between machines.

## Controls: the harness has to fail once

A harness only counts after it has failed once. `ts-to-rust` lists the controls for the frozen suite; these are the
ones specific to this harness:

| Control | Expected failure |
|---|---|
| Make the legacy adapter in `ts-oracle.mjs` return a wrong answer | the `oracle_` test fails and shrinks to a minimal input `[re-run]` |
| Point `root` or `pattern` at nothing | the harness panics `no test cases found` rather than passing `[derived]` |
| Run an `oracle_` test where `node` is missing | the test panics and does not skip: the template's `spawn()` ends in `.expect(..)` `[derived]` |

## Traps `ts-to-rust` does not carry

Integer range, `Math.round` ties, default sort, string length, dates, key order and `trim` are in that skill's
`references/json-fidelity.md`.

- **`toFixed` vs `format!`** `[re-run]`, Node v26.9.0 and rustc 1.98.1:

  | Expression | JS `toFixed` | Rust `format!` |
  |---|---|---|
  | 0.5 to 0 places | `"1"` | `"0"` |
  | 2.5 to 0 places | `"3"` | `"2"` |
  | 0.125 to 2 places | `"0.13"` | `"0.12"` |
  | 0.375 to 2 places | `"0.38"` | `"0.38"` (same) |

  At an exact tie JS takes the neighbour that is larger **in magnitude** (it handles the sign first, so negative ties
  round away from zero `[derived]`); Rust takes the even one. They disagree only on exact ties whose even neighbour is
  the lower one `[derived]`, and negative ties mirror the table. Put ties of both kinds, positive and negative, in
  the fixtures, and port the JS rule explicitly rather than trusting `{:.N}`.
- **Regex.** JS patterns may use lookbehind and backreferences; the `regex` crate does not support them (use
  `fancy-regex` only where needed) `[zip]`; `ts-to-rust`'s `type-map.md` notes the gap unverified. Give every ported
  pattern fixtures.
- **ICU.** `localeCompare` and `Intl` results depend on the ICU data Node ships `[derived]`, so oracle answers can
  change with the Node version.
