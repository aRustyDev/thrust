# bd-equivalent/SPEC-0001: command structure of the Thrust agent CLI

Status: **proposal**, 2026-11-14. The six owner decisions below are recorded as given; everything else is a
proposal awaiting owner review. Nothing here is built.
Input: [research 0015](../research/0015-bd-command-taxonomy.md) (what `bd` 1.3.4 has and how it groups it) and
[research 0016](../research/0016-plane-clis-and-the-agent-cli.md) (what Plane's CLIs and the Thrust server say about
this proposal; the source of decision 6, rules 9 to 12 and the three `list` commands above the issue).
Per-command detail: [`artifacts/bd-1.3.4-to-thrust-command-map.md`](../artifacts/bd-1.3.4-to-thrust-command-map.md),
generated by [`scripts/map_commands.py`](../scripts/map_commands.py). The script holds the tree and the fate of all
297 bd paths; this page holds the rules and the reasons and does not repeat the listing.
Scope: the beads-equivalent commands only. Commands that manage the tracker itself (the plane-cli equivalents) are
out of scope, except reading: this CLI lists and shows every level.

## Purpose

The CLI is the agent layer's interface to Thrust: agents claim work and record progress with it, as they do with
`bd`, and people use the same tool to see how work is going (owner, 2026-11-14). `thrust` and the noun names on
this page are placeholders.

## Decided by the owner (2026-11-14)

1. **The levels.** Initiative > Project > Module > Epic > Issue > Task.

   | Level | What it is | Planned by | This CLI may | Depends on (Contrail `FEATURES.md`) |
   |---|---|---|---|---|
   | Initiative | | Exec, PM | read | F-E14: P2, a gap with no ADR |
   | Project | | PM, Eng | read | F-B02: P0, served by `/api/v1` |
   | Module | Groups issues by what a feature or fix needs | Eng, agents | read | F-B11: P0, no `/api/v1` route yet |
   | Epic | A special issue that groups other issues; may have none | Eng, agents | the same as an issue | F-E08, work item types: P1 |
   | Issue | May or may not belong to an epic | Eng, agents | read, comment, change state, decompose into tasks | F-B03: P0, served by `/api/v1` |
   | Task | The bead equivalent. Belongs to an issue; may have sub-tasks | Agents | everything | F-B03's `parent`; no task resource exists |

   The last column is not the owner's; it is what research 0016 found. F-B11 is titled "Modules (epics)", which
   treats as one thing what this decision separates.

2. **The write boundary** is the last column: tasks in full; issues limited to comment, state transition and
   decomposition into tasks; modules and above read-only.
3. **The workflow engine is out of v1**: bd's `formula`, `mol`, `gate`, `swarm`, `merge-slot`, `cook`, `promote`
   and `ship`.
4. **One typed ID space.** An ID carries its level, so `show`, `status` and `tree` take an ID from any level.
5. **Epics get issue-level writes.** An epic is a special issue, so it takes comment, state transition and
   decomposition into tasks; it is not read-only like a module.
6. **v1 enforces by the bot user's project role.** Thrust has no API key scopes in v1 (Contrail ADR-0052), so the
   server refuses what the agent's project role does not allow and nothing finer. See rule 6 for what that leaves
   to the CLI.

## Rules

1. **Noun, then verb.** Nouns are singular. Verbs come from a closed set: `create`, `list`, `show`, `update`,
   `delete`, `add`, `remove`, plus named state transitions.
2. **One way to do each thing.** A top-level alias is allowed only as a fixed spelling of one noun-verb command, and
   there are three: `ready`, `next`, `done`.
3. **A read never writes.** bd's `orphans --fix` and `duplicates --auto-merge` write from commands that otherwise
   only report. Holding this rule is what lets a command marked read be given to an actor that must not write.
4. **A state transition is a verb; a field edit is a flag.** `close`, `reopen` and `defer` carry rules, so they are
   commands. `assign`, `priority`, `tag`, `link`, `note` and the like are flags on `update` or cases of another
   command.
5. **One validation path.** Bulk input is `--from -` on the same verb: JSONL in, one result line per input line
   out, in order. A failed line does not stop the rest, and the exit code says that some lines failed. bd's `batch`
   applies a close rule that `close` inside the same batch does not (research 0015).
6. **Audience and effect are attributes of a command, not places in the tree.** Each command is marked human,
   agent, both or admin, and read, write or local. In v1 the server enforces the actor's project role (decision 6),
   which is coarser than these marks:
   - What the role refuses, the server refuses: an agent whose bot user is not a member of a project cannot write
     there.
   - What the role allows but decision 2 does not (editing an issue's fields, creating a module), the CLI does not
     offer. That is a convention: `api` and any other client can still do it. `api` is marked admin for that reason.
   - A read-only actor is a bot user with a role that cannot write, not a key. bd's `--readonly` has no closer
     replacement until keys have scopes.

   The marks stay in the table so that scopes, when they come, have something to enforce.
7. **The default help is the human set.** `help --all` adds agent and admin commands. bd does the reverse: the full
   list is the default and `bd human` is the short one.
8. **Output follows the terminal.** Tables on a TTY; JSON when piped or with `--json`, in a published schema
   (`schema`). Data goes to stdout and nothing else does: messages, hints and errors go to stderr, and in JSON mode
   an error is JSON. Exit codes are one published table (Open 8).
9. **A write takes IDs.** Names are for filters on a read. A name that does not resolve is an error and is never
   sent on as a literal, and nothing is matched approximately. Resolution happens on the server, so it costs no
   extra requests.
10. **Exit 0 means the write was applied.** A write the server refuses or ignores is a non-zero exit, with a code
    of its own when the cause is the actor's role. The check that holds this rule is a control: an actor whose role
    cannot write attempts each write command and every one must fail.
11. **One command is one request, and a create can be retried.** `task create` sends the task with its issue,
    parent, labels and dependencies together, so it cannot half-succeed. `--key` names the create; a second create
    with the same key returns the first task. Work items already carry such a key (`external_id` and its source).
12. **No prompts.** No command waits on stdin for a confirmation, with or without a terminal. A command that
    removes more than its name says states that in the first two lines of its help.

The groups of research 0015 served to audit bd, and they are not carried over as a structure because they mix four
axes: the object (issue, memory, config), the effect (create, read, update, delete), the audience (agent-only,
developer) and the storage (RAW, sync, maintenance). Rule 1 takes the first axis as the tree, rule 6 makes the
second and third attributes, and the fourth mostly goes away with the local store.

## What bd lacks

Nine proposed commands have no bd command behind them; the script lists them as gaps and fails if one gains or loses
a source.

- **`claim take`.** In bd a claim is a flag: `update --claim`, and `ready --claim` for the first ready issue. Both
  are atomic. Renewing, releasing and reaping are commands (`heartbeat`, `unclaim`, `reclaim`); taking is not.
- **`claim list`.** bd shows a claim only through an issue's status and assignee. A person asking "which agents
  hold what, and are they alive" has no command.
- **`ask create`.** In bd an agent raises a question by adding the `human` label.
- **`issue list`, `module list`, `project list`, `initiative list`.** bd has one level, and an epic is an issue
  type. Without the three lists above the issue, `show`, `status` and `tree` take IDs that no command can find, and
  `init` cannot link a directory without asking.
- **`auth login`, `auth logout`.** bd is local and has no credential. Here every write is attributed to the
  key's user.

Not commands, but also missing in bd:

- **A roll-up above the epic.** bd has `epic status`, `swarm status` and `mol progress`. `status <id>` is meant to
  answer at every level.
- **Memory scope.** bd's memories are workspace-wide.

Worth keeping from bd: `update --if-status` and `--if-assignee` (a conditional write that changes nothing and exits
13 on a mismatch), and the lease model of `heartbeat` and `reclaim` (a TTL, and a grace window before reaping).

## Open

1. **The ID format** that carries the level (decision 4), and whether a task ID shows its issue. The server's
   identifier (`KEY-N`) is per project and exists only for work items, so it does not carry a level.
2. **Leases.** The TTL, and whether expired claims are reaped by the server on a timer or by `claim reap`. bd's
   leases are node-local and enforceable only on the node that granted them; a server-held lease does not have that
   limit.
3. **`ask`.** Its own object, or a task with a marker as in bd.
4. **`activity record`.** What an agent may append, and its schema. Contrail's M2 plans outbox consumers for
   activity (`contrail/PLAN.md`); whether this stream is that one is not decided.
5. **Memory scope**: workspace, project, issue, or per agent.
6. **The binary's name**, and the noun for the lowest level (`task` is used here from the owner's wording).
7. **How it is built**: the crate, and which API it calls. Not addressed here. Two notes from research 0016: if
   any command is generated, generate it from the server's OpenAPI document and not from prose; and claims, leases,
   dependencies, memory and questions have no Plane endpoint, so their server API has to be designed first.
8. **The exit-code table.** bd's 13 for a conditional write that did not match is kept. The rest needs values:
   authentication, role refused, not found, validation, rate limited, some lines of a bulk write failed. Plane's two
   community CLIs disagree with each other, so there is nothing to inherit. With it: what the CLI does on HTTP 429
   (Thrust has a per-key limit).
9. **What a task is on the server.** Today it can only be a work item with a `parent`, on the same endpoint as an
   issue. Whether a task becomes a work item type (F-E08), its own resource, or stays a child work item decides
   whether the server can ever enforce decision 2.
10. **Whether a project role can be made to express decision 2**, or whether the convention of rule 6 stands until
    keys have scopes. Thrust's role matrix was not read for this page.
11. **`--dry-run`** on `task delete`, `data import` and `claim reap`. It is only honest if the server evaluates the
    request without applying it; a client that prints the request proves nothing about the outcome.
12. **What `task delete` removes**: sub-tasks, dependencies, a held claim.
13. **MCP as a second transport.** If it is one, each command needs destructive and idempotent marks beside
    audience and effect, and the script's table is where they go.
14. **`data import --from bd` and Contrail ADR-0085**, which accepts Beads sync at P1 (F-E25) through `/api/v1` and
    leaves its importer question open (Q-0085.2). One way in, not two.

## How the mapping was checked

```sh
uv run .agents/plans/bd-equivalent/scripts/walk_bd.py <outdir>                                       # [verified 2026-11-14] 297 paths, bd 1.3.4; not re-walked for the research 0016 changes
uv run .agents/plans/bd-equivalent/scripts/map_commands.py <outdir>/tree.json <out.md>               # [verified 2026-11-14] exits 0
uv run .agents/plans/bd-equivalent/scripts/map_commands.py <outdir>/tree.json <out.md> --self-test   # [verified 2026-11-14] exits 1
```

The script refuses to write unless every bd path resolves to a disposition, every target is a command of the tree,
no key names a missing path, and every command of the tree either has a bd source or is a listed gap. The
`--self-test` run deletes the entry for `sql` and failed with `UNMAPPED bd path: sql` and `NEW command with no bd
source and not in GAPS: api`. The first real run also failed, on `issue list`, `claim take` and `ask create`: three
proposed commands with nothing in bd behind them, which is how they came to be recorded as gaps. The three `list`
commands of research 0016 were added as gaps by hand; both runs were repeated after that change.

What the check does not show: that a disposition is right. It proves completeness, not judgment. The mapping was made
from help text; no bd command other than `--help` and `version` was run.
