# bd-equivalent/SPEC-0001: command structure of the Thrust agent CLI

Status: **proposal**, 2026-11-14. The five owner decisions below are recorded as given; everything else is a
proposal awaiting owner review. Nothing here is built.
Input: [research 0015](../research/0015-bd-command-taxonomy.md) (what `bd` 1.3.4 has and how it groups it).
Per-command detail: [`artifacts/bd-1.3.4-to-thrust-command-map.md`](../artifacts/bd-1.3.4-to-thrust-command-map.md),
generated by [`scripts/map_commands.py`](../scripts/map_commands.py). The script holds the tree and the fate of all
297 bd paths; this page holds the rules and the reasons and does not repeat the listing.
Scope: the beads-equivalent commands only. Commands that manage the tracker itself (the plane-cli equivalents) are
out of scope.

## Purpose

The CLI is the agent layer's interface to Thrust: agents claim work and record progress with it, as they do with
`bd`, and people use the same tool to see how work is going (owner, 2026-11-14). `thrust` and the noun names on
this page are placeholders.

## Decided by the owner (2026-11-14)

1. **The levels.** Initiative > Project > Module > Epic > Issue > Task.

   | Level | What it is | Planned by | This CLI may |
   |---|---|---|---|
   | Initiative | | Exec, PM | read |
   | Project | | PM, Eng | read |
   | Module | Groups issues by what a feature or fix needs | Eng, agents | read |
   | Epic | A special issue that groups other issues; may have none | Eng, agents | the same as an issue |
   | Issue | May or may not belong to an epic | Eng, agents | read, comment, change state, decompose into tasks |
   | Task | The bead equivalent. Belongs to an issue; may have sub-tasks | Agents | everything |

2. **The write boundary** is the last column: tasks in full; issues limited to comment, state transition and
   decomposition into tasks; modules and above read-only.
3. **The workflow engine is out of v1**: bd's `formula`, `mol`, `gate`, `swarm`, `merge-slot`, `cook`, `promote`
   and `ship`.
4. **One typed ID space.** An ID carries its level, so `show`, `status` and `tree` take an ID from any level.
5. **Epics get issue-level writes.** An epic is a special issue, so it takes comment, state transition and
   decomposition into tasks; it is not read-only like a module.

## Rules

1. **Noun, then verb.** Nouns are singular. Verbs come from a closed set: `create`, `list`, `show`, `update`,
   `delete`, `add`, `remove`, plus named state transitions.
2. **One way to do each thing.** A top-level alias is allowed only as a fixed spelling of one noun-verb command, and
   there are three: `ready`, `next`, `done`.
3. **A read never writes.** bd's `orphans --fix` and `duplicates --auto-merge` write from commands that otherwise
   only report. Holding this rule is what lets a read-only credential be trusted.
4. **A state transition is a verb; a field edit is a flag.** `close`, `reopen` and `defer` carry rules, so they are
   commands. `assign`, `priority`, `tag`, `link`, `note` and the like are flags on `update` or cases of another
   command.
5. **One validation path.** Bulk input is `--from -` on the same verb. bd's `batch` applies a close rule that
   `close` inside the same batch does not (research 0015).
6. **Audience and effect are attributes of a command, not places in the tree.** Each command is marked human,
   agent, both or admin, and read, write or local. The server enforces audience through the credential's scope. A
   read-only key replaces bd's `--readonly` flag.
7. **The default help is the human set.** `help --all` adds agent and admin commands. bd does the reverse: the full
   list is the default and `bd human` is the short one.
8. **Output follows the terminal.** Tables on a TTY; JSON when piped or with `--json`, in a published schema
   (`schema`).

The groups of research 0015 served to audit bd, and they are not carried over as a structure because they mix four
axes: the object (issue, memory, config), the effect (create, read, update, delete), the audience (agent-only,
developer) and the storage (RAW, sync, maintenance). Rule 1 takes the first axis as the tree, rule 6 makes the
second and third attributes, and the fourth mostly goes away with the local store.

## What bd lacks

Six proposed commands have no bd command behind them; the script lists them as gaps and fails if one gains or loses
a source.

- **`claim take`.** In bd a claim is a flag: `update --claim`, and `ready --claim` for the first ready issue. Both
  are atomic. Renewing, releasing and reaping are commands (`heartbeat`, `unclaim`, `reclaim`); taking is not.
- **`claim list`.** bd shows a claim only through an issue's status and assignee. A person asking "which agents
  hold what, and are they alive" has no command.
- **`ask create`.** In bd an agent raises a question by adding the `human` label.
- **`issue list`.** bd has one level, and an epic is an issue type.
- **`auth login`, `auth logout`.** bd is local and has no credential. Here every write is attributed to a key.

Not commands, but also missing in bd:

- **A roll-up above the epic.** bd has `epic status`, `swarm status` and `mol progress`. `status <id>` is meant to
  answer at every level.
- **Memory scope.** bd's memories are workspace-wide.

Worth keeping from bd: `update --if-status` and `--if-assignee` (a conditional write that changes nothing and exits
13 on a mismatch), and the lease model of `heartbeat` and `reclaim` (a TTL, and a grace window before reaping).

## Open

1. **The ID format** that carries the level (decision 4), and whether a task ID shows its issue.
2. **Leases.** The TTL, and whether expired claims are reaped by the server on a timer or by `claim reap`. bd's
   leases are node-local and enforceable only on the node that granted them; a server-held lease does not have that
   limit.
3. **`ask`.** Its own object, or a task with a marker as in bd.
4. **`activity record`.** What an agent may append, and its schema. Contrail's M2 plans outbox consumers for
   activity (`contrail/PLAN.md`); whether this stream is that one is not decided.
5. **Memory scope**: workspace, project, issue, or per agent.
6. **The binary's name**, and the noun for the lowest level (`task` is used here from the owner's wording).
7. **How it is built**: the crate, and which API it calls. Not addressed here.

## How the mapping was checked

```sh
uv run .agents/plans/bd-equivalent/scripts/walk_bd.py <outdir>                                       # [verified 2026-11-14] 297 paths, bd 1.3.4
uv run .agents/plans/bd-equivalent/scripts/map_commands.py <outdir>/tree.json <out.md>               # [verified 2026-11-14] exits 0
uv run .agents/plans/bd-equivalent/scripts/map_commands.py <outdir>/tree.json <out.md> --self-test   # [verified 2026-11-14] exits 1
```

The script refuses to write unless every bd path resolves to a disposition, every target is a command of the tree,
no key names a missing path, and every command of the tree either has a bd source or is a listed gap. The
`--self-test` run deletes the entry for `sql` and failed with `UNMAPPED bd path: sql` and `NEW command with no bd
source and not in GAPS: api`. The first real run also failed, on `issue list`, `claim take` and `ask create`: three
proposed commands with nothing in bd behind them, which is how they came to be recorded as gaps.

What the check does not show: that a disposition is right. It proves completeness, not judgment. The mapping was made
from help text; no bd command other than `--help` and `version` was run.
