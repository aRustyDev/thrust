# Spike 0003 — Auth slice in Rust: argon2id, a session row, CSRF, API keys and one OIDC login, on both targets

**Gates:** ADR-0050 (the Rust implementation behind its "BetterAuth-shaped" HTTP routes, round 29) and ADR-0052 (its S1 and K1 mechanics); also ADR-0051's `authorize` seam with the user-only `Principal` (FR-03).
**Questions:** Q-0050.4 and Q-0050.6 are answered in round 29 (FR-16): a hand-rolled Rust implementation, which is this spike; no import, and the `User`, `Profile` and `Account` tables are defined fresh. This slice is the evidence behind Q-0050.4's answer. Q-0052 and Q-0033 are answered; the slice exercises their mechanics.
**Timebox:** 2 working days. **Depends on:** spike 0001 (done); issue #36 (the user-only `Principal`, the session repository over the `Database` port, `KvSessionStore` deleted), which follows issue #35 (FR-02). Runs beside spike 0002; Postgres is enough to start. **Tracked as:** issue #38. **Owner:** TBD.

**Round 29 (FR-16, FR-03): rewritten.** The round-21 version evaluated three ways to get BetterAuth with a Rust backend. BetterAuth is a TypeScript library, and its Rust port `better-auth-rs` is a community alpha whose wasm32 support is undocumented (`research/0002` §2). The owner's P0 is user+password only, with database sessions and no cache (round 25). FR-16 therefore turns the spike from a framework evaluation into a two-day auth slice: options A and B are dropped, and C is the plan. "BetterAuth-shaped" now means BetterAuth's HTTP shapes only (ADR-0050, round 29). The slice runs through FR-03's user-only `Principal`, so it waits for issue #36. The old schema-mapping step is closed by Q-0050.6, and the old Dioxus-client step moves to spike 0007 (its step 5 uses this result).

## Question
Can hand-rolled Rust deliver the P0 credentials (user+password hashed with argon2id, a database session behind an HttpOnly cookie with a CSRF double-submit token, hashed API keys as `X-Api-Key`) and one OIDC login, with the same behaviour on the wasm32 Worker and the native server, inside the Worker's default CPU limit?

## Options
- ~~**A. `better-auth-rs`**~~ **Dropped (round 29, FR-16).** A community alpha (`1.0.0-alpha.3`) over SeaORM with undocumented wasm32 support (`research/0002` §2); SeaORM is rejected for the data layer (ADR-0044, round 29).
- ~~**B. TypeScript BetterAuth as a service-bound identity Worker**~~ **Dropped (round 29, FR-16).** A second language and a second deployable; the round-29 non-Rust register does not carry it (ADR-0006, round 29).
- **C. Hand-rolled Rust: the plan.** Core code over the `Database` port, which is where identity sits after FR-05 (ARCHITECTURE §1c, round 29); sessions are rows (FR-03). It borrows BetterAuth's HTTP shapes, not its schema (Q-0050.6). Crates: an argon2id implementation (for example the RustCrypto `argon2` crate, pure Rust, so one build serves both targets [inferred]) and `openidconnect` 4.x for OIDC.

## Method
Every step runs on the four targets of `scripts/contract.sh` (`native-memory`, `native-pg`, `worker-memory`, `worker-cf`) unless it says otherwise. The tests go into the one HTTP contract suite (`thrust-contract-tests`); there is no second suite. The local Worker targets run on `wrangler dev`, so step 1's CPU measurement also needs one deployed run.

1. **argon2id with OWASP parameters, measured on the real platform.** Parameters: OWASP's minimum, m = 19 MiB (19,456 KiB), t = 2, p = 1, and its four equivalent trade-offs, from m = 46 MiB with t = 1 down to m = 7 MiB with t = 5 (OWASP Password Storage Cheat Sheet). Measure all five on a **deployed** Worker, because CPU limits are enforced only on Cloudflare's network, not in local development (workers/wrangler/configuration/#limits). Read CPU time per invocation from Workers Logs or the Tail Worker and Logpush trace events (workers/platform/limits/#cpu-time). The deployed run uses spike 0001's Stage 2 setup (`scripts/stage2-contract.sh`, `thrust-pg-dev` through Hyperdrive); those resources were deleted after that run, so it shares spike 0002's `worker-pg` deployment or recreates it from `research/0004` §10.7. Report CPU ms per sign-in (p50 and p99) for each configuration, on the Worker and natively. The default limit on Workers Paid is 30 s of CPU per HTTP request, configurable up to 5 minutes (workers/platform/limits/#cpu-time); the slice keeps the default. Also record memory: the 128 MB per-isolate limit includes WebAssembly allocations and is shared by the isolate's concurrent requests (workers/platform/limits/#memory), so the number of concurrent sign-ins one isolate can hash at the chosen m is part of the result [inferred].
2. **Session row, HttpOnly cookie, CSRF double-submit (ADR-0052 S1).** On issue #36's session repository. Sign-in for a seeded user with a password issues a fresh opaque session id (so no fixation) in a cookie with `HttpOnly`, `Secure` and `SameSite` set; the row is authoritative and read on every request; 30-day lifetime; sign-out sets `revoked_at` on the row, sign-out-everywhere on all the user's rows; `last_seen_at` is updated lazily (FR-03). CSRF: a double-submit token checked on cookie-authenticated mutations (ADR-0052). Plane hands out its token as JSON from `GET /auth/get-csrf-token/` because its CSRF cookie is HttpOnly (`apps/api/plane/authentication/views/common.py:28`, `apps/api/plane/settings/common.py:384`), and the React auth client already calls that route (`packages/services/src/auth/auth.service.ts:34`). Tests: a revoked session gets 401 on the next request; a deactivated user's session is rejected; a mutation without the token, or with one that does not match the cookie, is refused; sign-out-everywhere ends the user's other sessions. The local targets serve plain HTTP on `127.0.0.1`, so the suite asserts the attributes on `Set-Cookie` and sends the cookie back itself rather than through a client cookie jar, which would withhold a `Secure` cookie over HTTP [inferred].
3. **Hashed API keys accepted as `X-Api-Key` (ADR-0052 K1).** Create returns a high-entropy token with a visible prefix, once; only its SHA-256 hash is stored, looked up through an index; `last_used_at` is updated asynchronously. A key resolves to its user, as Plane's `APIKeyAuthentication` resolves an active, unexpired key of an active user (`apps/api/plane/api/middleware/api_authentication.py:29-43`). Tests: a revoked key gets 403 on the next request, Plane's status (the oracle answers 403 for an invalid, expired, revoked or inactive-owner key and 401 only for a missing one, ADR-0033 round 27; the 401 in ADR-0052's Confirmation was wrong and is corrected by issue #38), while an unrevoked key gets 200; no plaintext column exists; an expired key and a deactivated user's key are rejected; a key works with no OIDC configured (ADR-0050 Confirmation).
4. **One OIDC authorization-code login through `openidconnect`, against Zitadel or a mock IdP.** Authorization code with PKCE, discovery through `.well-known/openid-configuration`, `sub` linked through `Account(provider, provider_account_id)`, and a verified email required (ADR-0050 Decision). The login ends in the same session row and cookie as step 2. The suite drives it against a mock IdP that the test process serves on `127.0.0.1`, on all four targets; one manual login against Zitadel proves interoperation (K2). Feasibility only: OIDC lands at P1 (ADR-0050 A1), and JIT provisioning with it (Q-0050.1). `openidconnect` takes its HTTP client through the `AsyncHttpClient` trait, and `reqwest` is only its default feature (docs.rs, `openidconnect` 4.0.1), so natively the slice uses `reqwest` and on the Worker a client built on `worker::Fetch` (K1). Tests: a callback with an unverified email is rejected; a callback with a wrong `state` is rejected.
5. **Through the user-only `Principal` and `authorize` (FR-03).** The cookie, the `X-Api-Key` and the OIDC login all produce `Principal { user_id }`. `authorize` resolves the workspace from the URL slug through the membership query and returns the `Scope` (ADR-0051, round 29); no auth logic in handlers. Test: one user who is a member of two workspaces reaches both with one session, and is refused in a workspace where they have no membership.
6. **Security checklist,** written into the result: the argon2id parameters (step 1); session fixation (step 2); CSRF (step 2 and K3); the cookie attributes; rate limiting of the sign-in route through the round-29 limiter, which is the Workers Rate Limiting binding on Cloudflare and an in-process counter natively (ADR-0033, round 29); and an unknown email costing the same hash work as a wrong password, so sign-in timing does not reveal which emails exist [inferred].
7. **Controls.** A check that cannot fail is not evidence (AGENTS.md, rule 8). Show, through the contract suite's mutation controls (`scripts/mutants.sh`), that the suite fails on at least three broken builds: the `revoked_at` check skipped, a mutation accepted without a CSRF token, and an unverified email accepted. Raise the main pass's expected count (`EXPECT_MAIN` in `scripts/contract.sh`, and `EXPECT` of the `main` pass in `scripts/stage2-contract.sh`) by the number of new tests, so the vacuity guard still holds. (At the time of writing the counts were 15; issue #36 had already raised them to 21, and issue #38 raised them to 37 and 31: the deployed pass cannot run the six `oidc_` tests, because the mock identity provider is on `127.0.0.1`.)

## Known unknowns and risks
- **K1. `openidconnect` on wasm32. The known unknown.** On the Worker its HTTP calls (discovery, token exchange, JWKS) need a client built on `worker::Fetch`, implementing `AsyncHttpClient`. The crate's documentation does not mention wasm32 (docs.rs, 4.0.1). The client belongs in the Cloudflare adapter crate, so core code imports no `worker::*` (ARCHITECTURE §2 rule). Whether the crate and its dependencies build for `wasm32-unknown-unknown` with `default-features = false`, and whether the client's futures meet the `Send` rule the ports follow (ADR-0002; spike 0001 met the same question), is found out on day one [inferred]. If the build fails, the slice names the blocking crate; user+password and API keys do not depend on it.
- **K2. Zitadel is WARP-only.** `id.auth.woven` is a private `.woven` hostname (ADR-0050 Context). The browser redirect works for a user on WARP, but discovery, the token exchange and the JWKS fetch come from the server, so a deployed Worker needs a route to the issuer [inferred]. The manual Zitadel login therefore runs from a local target on a WARP-enrolled machine, and the suite uses the mock IdP. How a deployed Worker reaches the issuer is recorded for M6 (review §3).
- **K3. CSRF on the stock React app's JSON calls.** Plane disables the CSRF check on its REST API (`apps/api/plane/authentication/session.py:10`), and the React app sends the token only on its auth form posts and `set-password` (`packages/services/src/auth/auth.service.ts:79,122`). ADR-0052 checks the token on every cookie-authenticated mutation, so the stock app's JSON mutations would be refused until its service layer (a Q-R2 change area, `research/0003` §9) sends the token. The slice records the gap for ADR-0052 and for M1's auth-client change; it does not decide it.
- **K4. argon2id CPU on wasm32.** WebAssembly may hash much more slowly than native [inferred]; step 1 measures it rather than assuming it. If no OWASP configuration fits the default limit with margin, the slice reports the numbers and stops: lowering the parameters below OWASP's list, or raising `limits.cpu_ms`, is an owner decision.

## Exit criteria
The slice passes only if all four hold:

1. **The contract suite passes on four targets:** the main pass, with the auth tests added, is green on `native-memory`, `native-pg`, `worker-memory` and `worker-cf`, with the expected count raised and every step-7 control failing the suite.
2. **argon2id fits the platform:** at OWASP's minimum or one of its equivalents, the p99 CPU time per sign-in, measured on the deployed Worker, fits the default 30 s limit with margin; the configuration and the numbers are recorded.
3. **Same behaviour on both targets:** steps 2 to 5 give the same status codes, cookie attributes and refusals on the Worker targets as on the native ones.
4. **One OIDC login:** the authorization-code login completes through `openidconnect` on both targets against the mock IdP, and once against Zitadel (K2).
