# Spike 0002 — Database engine (`worker-pg`: Postgres through Hyperdrive vs `worker-do`: one instance-level Durable Object with SQLite)

**Gates:** ADR-0040 (engine), ADR-0041 (isolation), ADR-0083 (FTS + trigram). ADR-0042, 0043, 0044 and 0045 were accepted in round 29 as built (FR-17, FR-07, FR-22); this spike confirms ADR-0043's FR-22 allocation order, and a `worker-do` win reopens 0042, 0044 and 0045 for the SQLite dialect.
**Questions:** Q-0040, Q-0040.1, Q-0040.6, Q-0041, Q-0083.1, Q-0006.6 (folded in, FR-16).
**Timebox:** 3.5 days for the `worker-pg` cell (round 27) plus 3 days for the `worker-do` cell (FR-04). **Depends on:** spike 0001 (done); issue #35 (the FR-02 `Scope` port shape, so both cells implement the final signatures); for `worker-pg`, the CNPG Postgres `thrust-pg-dev` with its tunnel and Workers VPC service (ADR-0094, bead `plane-byd.4`). **Tracked as:** issue #37. **Owner:** TBD.

**Round 29 (FR-04, FR-16, FR-07, FR-08, FR-22): rewritten.** Round 27 narrowed this spike to Postgres only (Q-0040.1). FR-04 reopens that narrowing with four facts found since: the Hyperdrive statement-flow constraint is documented, so it is permanent; TLS to CNPG is unauthenticated; availability now includes `woven-o11y`; and the first database-backed request on a fresh isolate takes about 0.6 s (`research/0004` §10.3, F7). The round-11 desk review rejected DO-SQLite only on grounds that assume one object per workspace, so an instance-level object gets a cell of its own. FR-16 folds Q-0006.6's Stage 2b into this spike. FR-07 decided the data layer, so step 6 is gone.

## Question
Which engine runs the P0 slice, measured on the real platform: Postgres (CNPG) through Hyperdrive, or one SQLite database inside one Durable Object for the instance, with the native twin on the same dialect? The data-layer half of the round-25 question is answered: hand-written SQL on `tokio-postgres` (ADR-0044, FR-07).

## Candidates
Two prototyped cells, both driven by the existing HTTP contract suite (`thrust-contract-tests`, main pass 15 tests) and the existing `bench` (`crates/thrust-contract-tests/src/bin/bench.rs`, `bench <iterations> <concurrency>`). The suite is HTTP-only and target-agnostic (ADR-0121, round 26), so a cell is a deployment, not a new suite.

- **A. `worker-pg`: Postgres through Hyperdrive.** The slice as built: CNPG `thrust-pg-dev` reached through Hyperdrive, the Workers VPC service and the tunnel (ADR-0094). `scripts/contract.sh` calls this target `worker-cf` (`scripts/contract.sh:5,96`); the deployed run uses `scripts/stage2-contract.sh`, as spike 0001's Stage 2 did. The Stage 2 resources were deleted at the end of that run (`crates/thrust-worker/wrangler.stage2.toml:3`), so this cell recreates them from the ledger in `research/0004` §10.7 (new ids) and tears them down in the order recorded there (queue consumer, Worker, queues, then the rest). The Worker runs with `placement.region = "aws:us-east-1"` (FR-08, issue #39). Native twin: the `native-pg` target.
- **B. `worker-do`: one instance-level Durable Object with SQLite.** One object for the instance (single org, ADR-0003) holds the SQLite database. The `fetch` Worker forwards every API request to it; the shared axum router and the use-cases run inside the object over a SQLite adapter behind the `Database` port (workers-rs `Storage::sql()`, which the spike's two objects already use, `crates/thrust-worker/src/durable.rs:34,57`). Native twin: the same SQL on `rusqlite` in the native binary, as a new `native-sqlite` target of `scripts/contract.sh`, so both sets share one dialect. No tunnel, VPC service, Hyperdrive, TLS question or cluster coupling. Backups: point-in-time recovery (30 days) plus a nightly dump to R2 from an alarm. The object is created with the location hint `enam` (`get_by_name_with_location_hint`, workers-rs 0.8.7 `src/durable.rs:169`). Only the first `get()` honours a hint, and an object does not move after creation (durable-objects/reference/data-location), so the first deploy fixes its region.
- **C. D1:** desk review only, unchanged since round 27: `batch()` atomicity, no interactive transactions (FR-04).
- **D. DO-SQLite per workspace (ADR-0040 Option 3):** not prototyped. Cell B replaces it: the round-11 objections (cross-workspace fan-out, migrations across all objects, self-hosted emulation) assume one object per workspace.

## Method (both cells; seed ≈100k work items, 50 users)
Step numbers are kept from round 25, so references elsewhere (FR-22's "step 2", FR-08's "step 7") still resolve.

1. ~~Schema subset~~ **Replaced (round 29).** Both cells use the slice's schema as built: the six tables of `crates/thrust-adapters-postgres/migrations/0001_init.sql`, and a SQLite translation of the same file for `worker-do` and `native-sqlite`. The states, labels and join tables of the round-25 list are not added: the spike measures the slice, and ADR-0040 S3's grouped listing is measured at M1 under the same round-trip budget (step 7).
2. **`sequence_id` allocation under concurrent creates: the 50-writer create test.** 10k creates from 50 parallel writers in one project: monotonic, no duplicates, never reused after delete or move (Plane: `MAX(IssueSequence.sequence)+1`), `sort_order` allocated in the same critical section (R-F2). FR-04's text says 20 writers; R-F2, ADR-0040 S1 and this spike say 50, and 50 is the test. `worker-pg` uses ADR-0043's B1 counter row in the FR-22 order (its own short transaction, or `UPDATE … RETURNING` as the last statement); advisory locks are not a candidate (unsupported through Hyperdrive, FR-04). `worker-do` allocates inside the object, serialised by construction. **FR-22 allocation-order check:** create p95 at c=1 and c=8 with `bench` on `worker-pg`, before and after the reorder (round 26: 296 ms and 559 ms, `research/0004` §10.3), and once on `worker-do`.
3. **Partial unique indexes** and soft-delete uniqueness behave as Plane's, in both dialects: `work_items_external_live` frees the external key on soft delete, and `work_items_project_seq` never frees a number. SQLite has partial indexes (Q-0040.3).
4. **FTS plus substring parity** (ADR-0083): `tsvector`/GIN plus `pg_trgm` on `worker-pg`; FTS5 with the `trigram` tokenizer on `worker-do` and `native-sqlite`. Plane's search is `icontains`. Query `work_items.name` and `description` through a search route added to the slice for both cells; check substring and prefix parity, ranking and 1-minute freshness. The Durable Object docs list FTS5 (durable-objects/api/sqlite-storage-api) but not the trigram tokenizer, so check first that workerd's SQLite has it [inferred].
5. ~~Transactions~~ **Dropped for `worker-pg` (round 29).** ADR-0045 is accepted as built (explicit `Tx`, the outbox row in the same transaction), the slice already proves outbox atomicity on Postgres (review §4), and Q-0045.1 is answered (FR-22: serializable isolation only for allocation, which is a single statement). For `worker-do` the question is open: risk R1.
6. ~~Rust data layer on `wasm32`~~ **Dropped (round 29, FR-07).** Decided: hand-written SQL on `tokio-postgres` with typed parameters through one `Pg` wrapper, no ORM (ADR-0044, accepted). On `worker-do` the adapter is the workers-rs SQL API, and `rusqlite` natively.
7. **Latency.** p95 for create, list and activity from `bench` at 100k items, at c=1 and c=8 as `scripts/contract.sh <target> bench` runs it (`scripts/contract.sh:218-219`), measured as SPEC §6.4 defines it: warm path, from the origin's region; the first database-backed request on a fresh isolate, or on a freshly started object, is reported separately. **Placement re-run (FR-08), `worker-pg`:** with `placement.region = "aws:us-east-1"` and without it; this replaces round 25's Smart Placement on/off and the open half of Q-0040.5. **Hyperdrive caching on versus off (Stage 2b), `worker-pg`:** caching needs its own Hyperdrive config (ADR-0040, round 27). **Distant region (Stage 2b), both cells:** the same bench from a distant region beside the origin-region run. **Round-trip budget (FR-08, issue #39):** a counting `Connector` in the contract suite asserts that the list endpoint makes at most 5 database round trips on `worker-pg`. On `worker-do` a request makes one Worker-to-object hop and its statements run inside the object; the cell reports both counts.
8. ~~Tenant isolation hypothesis~~ **Dropped (round 29, FR-02).** The tenant guard is the `Scope` argument of every repository and `Tx` method (ADR-0041 and ADR-0045, round 29; issue #35), and the two-tenant property test stays. RLS cost is not measured.
9. **Cost projection** at the sizing target, Cloudflare side; the Postgres host is reported separately, outside the envelope (round 27). **24-hour run (Stage 2b):** one per cell, with the projection reconciled against the account's usage rather than inferred from counts as in `research/0004` F8. `worker-do` adds Durable Object requests, duration and SQLite storage, which is billed since January 2026 (FR-04). The owner of the schema-per-PR cleanup on the shared dev database is issue #57 (Q-0094.7).
10. **Real email send (Stage 2b; new).** One send through the Email binding on whichever cell is deployed. It needs an owned sender domain and a verified destination (`research/0004` F9), and it does not depend on the engine. `--panic-unwind`, also listed in Q-0006.6, is not folded in: the review found the `panic=abort` policy sound for P0 (§4).
11. **Migration story (new; an exit criterion).** `worker-pg`: the `migrate` binary applies the SQL migration files, expand before contract (ADR-0042), in ADR-0110's deploy order. `worker-do`: the object applies the same versioned SQL files the `rusqlite` twin applies, on start, inside `blockConcurrencyWhile` (workers-rs `State::block_concurrency_while`, `src/durable.rs:339`; the docs reserve it for initialization and migrations, durable-objects/best-practices/rules-of-durable-objects). Each cell applies one expand and one contract migration to the seeded store and shows what happens when a migration fails halfway.

## Risks for the `worker-do` cell
- **R1. How ADR-0045's explicit `Tx` maps onto the object. Open; the cell must answer it.** `sql.exec()` cannot run `BEGIN TRANSACTION` or `SAVEPOINT`; the docs send callers to `ctx.storage.transaction()` or `ctx.storage.transactionSync()`, and the `transactionSync` callback must complete synchronously (durable-objects/api/sqlite-storage-api) [verified]. workers-rs 0.8.7 binds no `transactionSync`. It exposes an async `Storage::transaction` whose closure and future must be `'static` (`worker-0.8.7/src/durable.rs:635-654`; `worker-sys-0.8.7/src/types/durable_object/storage.rs:54`) [verified in the local cargo registry]. ADR-0045's `Tx` is an object that `Database::begin()` returns and the use-case drives across awaited calls before it commits or drops it; a `Tx` dropped without `commit` must roll back (`crates/thrust-ports/src/lib.rs:102,140-157`). Neither binding takes that shape directly. Candidates [inferred]: bind `transactionSync` by hand through `Storage::as_raw()` and run the transactional part of the use-case synchronously inside it; move owned state into `Storage::transaction`; or rely on the documented rule that writes with no intervening `await` are submitted atomically (same docs page). The chosen mapping must pass a must-fail control: an error after the work-item insert and before commit leaves neither the row nor its outbox entry.
- **R2. One object serialises the instance.** Every request runs through one object in one location; the database is single-region today anyway (FR-04). The 50-writer test and the c=8 bench measure the queue this creates; nothing about it is assumed.
- **R3. The trigram tokenizer may be missing** from workerd's SQLite (step 4) [inferred]. Without it, substring parity falls back to plain `LIKE`, the SQLite analogue of ADR-0083's `ILIKE` fallback.
- **R4. Sunk and new costs.** The live CNPG work becomes unused if this cell wins, and SQLite storage billing applies (FR-04).

## Exit criteria (per cell)
Precondition: the HTTP contract suite's main pass is green on the deployed cell and on its native twin (`native-pg` or `native-sqlite`), and step 3 holds. A cell then passes only if it meets all five:

1. **50-writer create test:** no duplicate `sequence_id` in 10k creates from 50 parallel writers in one project, no number reused after delete, `sort_order` in the same critical section.
2. **FTS plus trigram:** substring and prefix queries return Plane's `icontains` results on the seed, with 1-minute freshness (`pg_trgm` on `worker-pg`, the FTS5 trigram tokenizer on `worker-do`).
3. **List p95 < 300 ms from the origin region** at 100k items on the warm path (headroom to the 500 ms SLO), with cold first requests reported beside it.
4. **Migration story:** step 11 exercised once, the failure case included.
5. **Projected cost** within the envelope at the sizing target (Cloudflare side; the Postgres host separately), reconciled against the 24-hour run.

Reported, not pass or fail: the FR-22 allocation-order check and the placement re-run (ADR-0043 and FR-08 take their numbers), caching on versus off, the distant-region bench, the round-trip counts (the contract suite enforces the budget once issue #39 lands) and the email send.

## Decision rule
- **Postgres (`worker-pg`) stays the default if the `worker-do` cell fails any exit criterion** (owner, review §5, FR-04).
- **If both cells pass, Q-0040.6 decides** (an owner question added to QUESTIONS.md in round 29).
- If `worker-pg` fails a criterion, that is a finding against the default; it goes to the owner under Q-0040 with both cells' numbers.
