# ADR-0081: Upload flow, image handling and export delivery

## Context and Problem Statement

Plane's upload path is presign → client PUT → confirm, with `FileAsset` rows created first and `delete_unuploaded_file_asset` (daily 02:00) removing rows that never completed;
asset metadata (size/type) is read back by `get_asset_object_metadata`; exports (`ExporterHistory`) are written to S3 and links expire via `delete_old_s3_link` **[S]**. We need the
equivalent flow on the `BlobStore` port (ADR-0080) that fits Workers limits and the `FileAsset` contract (ADR-0047).

## Decision Drivers

* Large files must not pass through the API Worker.
* Server must validate type/size/ownership and authorize every download (private workspaces).
* Orphan cleanup and expiry for exports must be automatic.
* Same UX contract for the kept frontend (it expects presigned-style responses today).

## Considered Options

* Option 1: **Direct-to-store presigned PUT** (+ multipart for large), then client `confirm` call; completion also verified by storage event/head
* Option 2: **Worker-streamed upload** (client → API Worker → R2 binding) with size cap
* Option 3: **Upload sessions in a Durable Object** (resumable, chunked, server-coordinated multipart)
* Option 4: Hybrid: Option 1 for files > N MB, Option 2 for small (avatars/inline images) to avoid CORS and double round trips

## Decision Outcome

**Decision (accepted, round 29): the leading hypothesis, Option 4 (hybrid): small files (inline images, avatars) in a single call through the API, attachments by presigned PUT/multipart where the blob adapter supports presigned uploads; exports as a long job on the `Queue` port (ADR-0071, round 29). Per FR-17, `reviews/2026-10-19-fable-architecture-review.md` §5.**

Leading hypothesis (accepted): **Option 4** (confidence: medium) — inline editor images and avatars are small and benefit from a single call;
attachments use presigned PUT/multipart, which keeps the frontend contract.

Exports: generated by a Workflow (ADR-0071), streamed into `BlobStore` under a tenant-prefixed key, delivered via short-lived presigned GET (or Worker-proxied download with auth), expired by
a Cron job (ADR-0072).

### Consequences

* Good: presigned PUT supports objects up to 5 GiB single/5 TiB multipart on R2 and expiry 1 s–7 days; the Worker never carries the body.
* Bad: presigned URLs aren't usable on R2 custom domains and POST forms are unsupported (R2 docs), so the browser must PUT to the S3 endpoint — needs bucket CORS and exposes the storage hostname.
* Bad: Option 2 is bounded by Workers inbound request limits (plan-dependent).
* Neutral: image resizing/transcoding (Cloudflare Images binding exists in CF docs) is optional and out of the port; see Q-0081.

### Confirmation

* E2E: upload 1 KB, a file at the **5 MB default limit**, an over-limit file (rejected at create and confirm), and — with the limit raised in test config — 50 MB (multipart) via the kept frontend against both adapters; interrupt and resume a multipart upload.
* Cleanup test: abandoned `FileAsset` row and abandoned multipart are removed within the retention window.
* Authorization test: user A cannot obtain a GET URL for workspace B's asset.

## Pros and Cons of the Options

### Option 1: Direct presigned

* Good: offloads bytes; matches Plane. * Bad: CORS/credential handling; two-phase state machine.

### Option 2: Worker-streamed

* Good: one call, full control (validation on bytes, virus scan hook). * Bad: request size limits, CPU/time, cost; hot path through Worker.

### Option 3: DO upload sessions

* Good: resumable with server-side state. * Bad: complexity; no self-hosted twin without another coordination service.

### Option 4: Hybrid

* Good: best fit per asset class. * Bad: two paths to test; threshold tuning.

**No virus scanning of uploads** at v1 (Q-0081.1).

## Update — review fixes, round 25 (2026-10-18)

Defaults aligned with rounds 16–20: default max asset size **5 MB per instance** (configurable); **no virus scanning** at v1; exports are **CSV/JSON via a Workflow (P1) with 24-hour links**, size ceiling starting at 100 MB; public-board assets go through the Worker proxy (ADR-0080). The ADR stays `proposed` (flow choice still open).

## Update — spike results, round 26 (2026-10-18)

Spike 0001 constraint: the Worker root buffers (and bounds at 8 MiB) every request body, so an upload through the Worker is buffered, not streamed (ADR-0080). The 5 MB default asset limit fits under that bound; anything larger needs presigned PUT or a separate streaming route. This favours presigned PUT as the default path; Q-0081 stays open.

## Update — review round 29 (2026-10-19)

Per FR-17 (`reviews/2026-10-19-fable-architecture-review.md`; the owner's decision is its §5 table: apply now, "every acceptance cites this review as the recorded owner decision"), this ADR is accepted on its leading hypothesis, quoted in the Decision Outcome: "Option 4 — inline editor images and avatars are small and benefit from a single call; attachments use presigned PUT/multipart, which keeps the frontend contract." Q-0081 is answered. FR-17 names 0081 among the open questions whose default is already in their own text.

**Presigned uploads exist only where the blob adapter supports them.** On the self-hosted set at P0 the `BlobStore` adapter is local disk inside the native binary (ADR-0080, round 29; FR-19), and local disk has no presigned PUT: there is no SigV4 endpoint to sign for. Where the adapter has no presigned PUT, every upload takes Option 4's single-call path through the API, inside the configured `max_size` (5 MB by default, ADR-0047) and under the 8 MiB request-body bound that the shared router sets on both targets (`DefaultBodyLimit`, `crates/thrust-api/src/lib.rs:292`). Uploads above that bound need the R2 adapter on the Cloudflare set or the S3-compatible adapter at P1 (MinIO or S3), which support presigned PUT. This answers the point ADR-0080's round-29 note left open under Q-0081. Neither path is built yet: the `BlobStore` trait in the code has no presign method (`crates/thrust-ports/src/lib.rs:200-204`).

**Exports** are a long job on the `Queue` port with a `jobs` table for state (ADR-0071, round 29; issue #56), not a Workflow. This supersedes the Decision Outcome's "generated by a Workflow (ADR-0071)", the round-25 note's "via a Workflow (P1)" and the Workflow step limits named in Q-0081.2. The rest of the export paragraph (tenant-prefixed key, short-lived presigned GET or Worker-proxied download, Cron expiry) stands; where the adapter has no presigned GET, the download is proxied with auth.

**Image transforms** stay optional and outside the port (the Consequences' Neutral item); none is built at P0. Cleanup of unuploaded assets is the Scheduler reaper of ADR-0047.

The Confirmation's e2e "against both adapters" is narrowed by Q-0123.2's answer (ADR-0123, round 29): e2e runs on the Cloudflare set only, and the self-hosted set is covered by the contract suite's `native-pg` cell. The 50 MB multipart case therefore runs against R2.
